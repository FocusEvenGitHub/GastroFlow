# Technical decisions

Decisions with a real trade-off, not a stack list. See [`docs/architecture.md`](architecture.md) for how each of these plays out in the running system. Short versions of the top picks are in the [README](../README.md#technical-decisions).

| Decision | Why | Trade-off / cost |
|---|---|---|
| Slim 4 micro-framework, not a full framework | Routing/middleware/DI without adopting everything a framework like Laravel brings, for a project that started as raw PHP | No built-in test scaffolding, scheduler, or CLI tooling — those are added by hand as needed |
| Eloquent standalone (`Capsule\Manager`), not full Laravel | Familiar, expressive query builder/ORM without the framework around it | Pulls in several `illuminate/*` packages as implicit dependencies; no Laravel-style Schema-builder migrations |
| Hand-rolled `MigrationRunner` over plain `.sql` files, not an ORM migration framework | Schema changes are explicit SQL, easy to read as a diff, framework-agnostic | Forward-only — no `down()`/rollback semantics |
| `public/.htaccess` bypass for cashier/kitchen/admin views, instead of routing everything through Slim | Those pages are static Alpine.js shells that only need to call the JSON API — no reason to pay framework overhead for them | Two separate request-handling paths to reason about; anything needing CORS/auth middleware has to live under `/api/*` |
| ~~Signal-file SSE instead of Redis/RabbitMQ for kitchen live updates~~ — **corrected 2026-09-26**: replaced by a MySQL-backed `EventPublisher` (spec 041); row kept, struck through, rather than deleted, per this file's own discipline of correcting stale claims in place | Zero extra infrastructure for a single-location deployment | Was not safe under concurrent writes or multiple app instances — closed by spec 041; this row previously said the fix was only planned, which had gone stale |
| DB-backed `jobs` table + `bin/worker`, not a message broker | Avoids adding Redis/RabbitMQ for one background job type (printing) | Needs a long-running worker process — it runs as the `print-worker` compose service (spec 008), so `docker compose up -d` does start it, but queue mechanics that a broker gives for free (reservation timeouts, failed-state tracking, retention) had to be hand-rolled in `JobService` (spec 033) |
| `App\Money` (integer cents), not `bcmath`/a Composer money library | Avoided the proven binary-float drift in `PrintService`'s receipt totals with the smallest possible primitive — one small class, no new dependency, no schema change (`DECIMAL(10,2)` columns were already correct) | Not a general-purpose Money type — single currency (BRL), no allocation/split-cents helpers; would need extending if either becomes a real requirement |
| `bin/backup-db`/`bin/restore-db` shell out to the `db` container's own `mysqldump`/`mysql` from the **host**, not a PHP `bin/` script (spec 045) | The `web`/`print-worker` image has no MySQL client (only `pdo_mysql`) — adding one would be a new `apt` dependency for a self-hosted image, against this project's own "don't add dependencies unless explicitly asked" rule; the official `mysql:8.0` image already ships a proven `mysqldump`/`mysql`, so reusing it beats hand-rolling a PHP-based dump | Two of the project's only host-run (not container-run) scripts, breaking the otherwise-consistent "every `bin/*` script runs via `docker compose exec web`" pattern; requires a POSIX shell on the host (Git Bash/WSL/Linux/macOS — no native PowerShell/cmd.exe support) |
