# Technical decisions

Decisions with a real trade-off, not a stack list. See [`docs/architecture.md`](architecture.md) for how each of these plays out in the running system. Short versions of the top picks are in the [README](../README.md#technical-decisions).

| Decision | Why | Trade-off / cost |
|---|---|---|
| Slim 4 micro-framework, not a full framework | Routing/middleware/DI without adopting everything a framework like Laravel brings, for a project that started as raw PHP | No built-in test scaffolding, scheduler, or CLI tooling — those are added by hand as needed |
| Eloquent standalone (`Capsule\Manager`), not full Laravel | Familiar, expressive query builder/ORM without the framework around it | Pulls in several `illuminate/*` packages as implicit dependencies; no Laravel-style Schema-builder migrations |
| Hand-rolled `MigrationRunner` over plain `.sql` files, not an ORM migration framework | Schema changes are explicit SQL, easy to read as a diff, framework-agnostic | Forward-only — no `down()`/rollback semantics |
| `MigrationRunner` hashes migration content with line endings normalized (`\r\n` → `\n`) before comparing, and refuses to proceed on a mismatch (spec 048) | Catches an already-applied migration edited in place, without false-flagging a `.gitattributes` line-ending normalization (spec 034) as tampering — confirmed to happen for real: 10 of the 14 migrations that existed at `v1.7.1` differ from today's checkout by line endings alone | Any database migrated before this normalized-hash comparison shipped needs a one-time, explicit `bin/migrate --trust-current-hashes` before it will proceed again — confirmed against both the shared `restaurant_test` database and this project's own development database during spec 048 |
| `.gitattributes` alone governs line endings, not `core.autocrlf` (spec 049) | A per-developer git config setting can't be relied on — this repo's own local override existed on the very machine that still had CRLF-on-disk files. Explicit `eol=lf` per path is versioned and applies regardless of any developer's config | A CRLF blob committed *before* a path's `eol=lf` rule existed is never retroactively fixed by the attribute alone — needs an explicit one-time `git add --renormalize .` commit, done for the 9 affected files during spec 049; a genuinely CRLF-on-disk working tree (distinct from a CRLF blob) needs a full local re-checkout, which no repository-side fix can force |
| `public/.htaccess` bypass for cashier/kitchen/admin views, instead of routing everything through Slim | Those pages are static Alpine.js shells that only need to call the JSON API — no reason to pay framework overhead for them | Two separate request-handling paths to reason about; anything needing CORS/auth middleware has to live under `/api/*` |
| ~~Signal-file SSE instead of Redis/RabbitMQ for kitchen live updates~~ — **corrected 2026-09-26**: replaced by a MySQL-backed `EventPublisher` (spec 041); row kept, struck through, rather than deleted, per this file's own discipline of correcting stale claims in place | Zero extra infrastructure for a single-location deployment | Was not safe under concurrent writes or multiple app instances — closed by spec 041; this row previously said the fix was only planned, which had gone stale |
| DB-backed `jobs` table + `bin/worker`, not a message broker | Avoids adding Redis/RabbitMQ for one background job type (printing) | Needs a long-running worker process — it runs as the `print-worker` compose service (spec 008), so `docker compose up -d` does start it, but queue mechanics that a broker gives for free (reservation timeouts, failed-state tracking, retention) had to be hand-rolled in `JobService` (spec 033) |
| `App\Money` (integer cents), not `bcmath`/a Composer money library | Avoided the proven binary-float drift in `PrintService`'s receipt totals with the smallest possible primitive — one small class, no new dependency, no schema change (`DECIMAL(10,2)` columns were already correct) | Not a general-purpose Money type — single currency (BRL), no allocation/split-cents helpers; would need extending if either becomes a real requirement |
| `bin/backup-db`/`bin/restore-db` shell out to the `db` container's own `mysqldump`/`mysql` from the **host**, not a PHP `bin/` script (spec 045) | The `web`/`print-worker` image has no MySQL client (only `pdo_mysql`) — adding one would be a new `apt` dependency for a self-hosted image, against this project's own "don't add dependencies unless explicitly asked" rule; the official `mysql:8.0` image already ships a proven `mysqldump`/`mysql`, so reusing it beats hand-rolling a PHP-based dump | Two of the project's only host-run (not container-run) scripts, breaking the otherwise-consistent "every `bin/*` script runs via `docker compose exec web`" pattern; requires a POSIX shell on the host (Git Bash/WSL/Linux/macOS — no native PowerShell/cmd.exe support) |
| Packaging fee = price of a menu item linked by `menu_items.packaging_option`, not a setting or a hardcoded constant (spec 050) | The client already edits "Embalagem Simples/Especial" as menu items in the Admin; reusing them means one place to change the price and no new settings UI. A dedicated column (not the item name) survives renaming | No UI to change which item is linked (migration/SQL only); deleting the item silently falls back to the old R$ 1,00/2,00; the kitchen's "Editar Pedido" re-prices packaging at the current price on save, so an edited old order can change value — **extended 2026-10-02 by spec 052**: that save now re-prices the item and add-on prices too (names stay snapshotted) |
| Admin pages share PHP `include` partials + one plain-JS session helper (`auth.js`), not a SPA or a frontend build (spec 051) | Keeps the existing "view scripts outside Slim" model and the no-build rule; one place for login/401/403 instead of three copies | Each page is still a full page load; local assets are cache-busted by file mtime (`?v=`) in `head.php` since there's no bundler to hash them; role-based sidebar hiding is cosmetic only |
| Connection indicator driven by a 5 s heartbeat on `/health/ready` plus the kitchen's `EventSource` state, not by the outcome of ordinary API calls (spec 057) | A screen idle between orders makes no calls, so it could never notice the server leaving; `/ready` instead of `/live` because a server whose database is down is just as unusable to the operator; ordinary calls' network failures only bring the next check forward | One `select 1` per open screen every 5 s; up to ~5 s between the server leaving and the pill changing; a stream that hangs while staying open (server alive, `stream.php` stuck) still reads "Conectado" — detecting it needs a server ping event, left as a follow-up |
| One shared plain-JS client (`GF` in `public/assets/js/gf.js`) for API calls, toasts and theme across cashier, kitchen and admin; no generic loading-state helper (spec 056) | Every screen had its own copy of the same fetch/parse/error/toast/theme code, and network or non-JSON failures surfaced as browser-internal text (`Failed to fetch`, `Unexpected token '<'`); loading flags are per-action page state, so a wrapper would add indirection without removing real duplication | Every call now fails as one normalized `Error`, so a screen that wants partial results (e.g. Relatórios' seven parallel requests) gets all-or-nothing instead; error texts come from the API, which still has some English messages (`Validation failed`) |
| Third-party frontend libraries vendored into `public/vendor/<lib>-<version>/` as their official minified files, not bundled with Vite/npm (spec 055) | Offline operation was the goal, and copying the upstream files reaches it with no Node toolchain in install/upgrade; the version in the directory name means a browser can never mix a cached old file with a new page | Upgrades are manual (download, swap paths, update the hashes in `public/vendor/README.md`); no tree-shaking, so the full builds (~1.7 MB, mostly Font Awesome webfonts) are committed |
| Login throttling in a MySQL table (`login_attempts`), keyed on client IP + username plus a per-IP cap, with `REMOTE_ADDR` as the IP (spec 053) | No Redis/cache in the stack, and failed logins are rare enough for a small indexed table; IP + username means an attacker can only lock an account out on their own IP, while the per-IP cap (30) stops username spraying | Under Docker Desktop all host traffic shares the gateway IP, so per-IP keys collapse there; proxy headers are ignored, so a future reverse proxy would need an explicit trusted-proxy setting; limits are code constants, not settings |
